# pitmhskills audit — 2026-10-21

Audited the router at `C:\Users\Mattchine\pitmhskills` (v0.2.4 layout, 2,178
cards), the MCP server, the prompt hooks, and every installed client
(OpenCode, Codex, Claude Code, Zed).

Everything below was reproduced against the live router. The reproduction
commands are in `docs/audit-2026-10-21-repro.md`.

## Summary

The router works. It is not the problem. The problem is in three layers.

**Delivery.** Four defects:

1. **`get_ref` is dead for every client.** It resolves `cards/<id>.json`
   relative to the server process working directory, so it always throws
   "unknown skill". Every routed body is a section map whose only content path
   is `get_ref`, so a picked skill arrives as a table of contents.
2. **Design tasks ask instead of pick, 6 out of 8 times.** The decision rule
   requires a score margin of 10 over the runner-up, and the design space in
   the library is full of near-duplicates. On `ASK` the OpenCode plugin sends
   the question without the body, and the intended fallback instruction never
   reaches the model, so the agent asks a human or proceeds bare. The three
   craft design skills (`taste-skill__design-taste-*`, `ibelick__ui-skills-root`)
   are tier C and can never be routed at all.
3. **The instructions that would fix the above are silently discarded.**
   `opencode.jsonc` puts prose in `instructions`, but opencode v2 defines that
   key as "Additional paths or URLs supplying ambient instructions". The text
   is treated as a file path, does not resolve, and is dropped. Claude Code has
   no hook and no MCP server at all.
4. **Skills and reference material share one ranking.** A card like
   `accessibility-agents__kb-mobile-accessibility` declares itself "Reference
   data, not a reviewer" and still competes as if it were a procedure. There
   is no `kind` field, no separate channel, and no separate acquisition flow.

**Scoring.** The rarest words are not the rarest-scoring words:

> `idf()` is called with an already-stemmed token and stems it again
> (`src/lexicon-stats.ts:51`). Measured live: **"database" (19 cards) is worth
> 8.380; "wizard" (3 cards) is worth 6.434.** The rarer word scores lower,
> which is the exact inversion the design note at `src/weights.ts:29-34` says
> must never happen. Add an out-of-vocabulary word and a card loses about 19
> points, which is how a correct task turns into an ABSTAIN.

**The council.** It is the right answer to a tie and it works end to end, but
nothing routes an agent into it, it has never completed from a real agent
session, it reproduces the off-domain noise it was built to remove, and it
carries a path-traversal write and a prompt-injection path.

Above all of that: **the entire scoring system, lexicon, and council are
uncommitted.** The committed `src/serve.ts` at HEAD exposes four MCP tools
with no council. A `git clean` destroys the router that three clients are
being served by. That is the most urgent item in this audit.

## 1. The flow, end to end

```
task text
  └─> client integration           (hook | MCP call | nothing)
        └─> route(task, cwd, session)
              ├─ signals      stack/files detected from the repo, no LLM
              ├─ gate         tier / license / do_not_use_when drops
              ├─ retrieve     FTS5 BM25 + IDF-weighted vector arm, pool 40
              ├─ shortlist    near-duplicate dedup, max 8 per cluster
              ├─ score        cover 0.40 + bm25 0.35 + vec 0.05 + unknown 0.60
              ├─ decide       floor 45, margin 10, pick_floor 80
              └─ deliver      STYLE fence + byte-capped body + scope fence
```

`src/decide.ts:27-46` is the whole decision:

```ts
if (ranking.length === 0) return ABSTAIN;
if (top.score < floor) return ABSTAIN;          // floor = 45
const m = second ? top.score - second.score : 99;
if (top.score >= pickFloor && m >= margin) return PICK;   // pickFloor = 80, margin = 10
if (top.score >= floor && m >= margin) return PICK;       // identical outcome
if (top.score >= floor && second && m < margin) return ASK;
return ABSTAIN;
```

**`pick_floor` is dead logic.** Line 39 and line 40 have the same effect: if
the top score clears 80 with a margin of 10 it is a PICK at line 39; if it
clears 45 with a margin of 10 it is a PICK at line 40. The threshold changes
nothing. The same shape in the fixture, `config.json`, and the docs suggests
it was meant to be "a high-confidence top pick does not need the margin" or
the reverse. Either way it is not implemented.

**`vec` carries 5 % of the score** (`config.json` weights). Routing is
effectively lexical plus coverage. Semantic similarity between a task and a
skill barely moves the ranking, which is why near-duplicate skills that share
vocabulary land within the margin of each other and force an `ASK`.

## 2. Why agents failed to pick up skills

### 2.1 `get_ref` throws "unknown skill" for every skill (critical)

```ts
// src/serve.ts:79-90
const base = skill_id.replace(/[^a-zA-Z0-9_-]/g, "");
const rel = path.replace(/\.\./g, "");
const cardPath = `cards/${base}.json`;              // ← relative to the process CWD
if (!existsSync(cardPath)) throw new Error("unknown skill");
const card = JSON.parse(readFileSync(cardPath, "utf8")) as { skill_path?: string };
const dir = card.skill_path?.split(/[/\\]/).slice(0, -1).join("/") ?? "";
const full = dir ? `${dir}/${rel}` : rel;
if (!existsSync(full)) throw new Error("ref not found");
```

The MCP server is launched by opencode, Codex, and Zed with the **client's**
working directory, not the router root. `cards/<id>.json` therefore resolves
to `<project>/cards/<id>.json`, which never exists.

Reproduced through the MCP tool:

```
get_ref apple-design-skill__apple-design / SKILL.md  -> Error: unknown skill
get_ref apple-design-skill__apple-design / references/x.md -> Error: unknown skill
get_ref nope__nope / x -> Error: unknown skill
```

The card exists at `C:\Users\Mattchine\pitmhskills\cards\apple-design-skill__apple-design.json`
and its `skill_path` is absolute
(`C:\Users\Mattchine\pitmhskills\skills\apple-design-skill\SKILL.md`), so only
the first lookup is broken. `src/deliver.ts:7` shows the correct pattern in the
same repository:

```ts
const ROOT = join(dirname(fileURLToPath(import.meta.url)), "..");
```

**Fix:** resolve `cardPath` against `ROOT`, and resolve `full` against the
card's absolute `skill_path` directory, refusing any result that is not
inside that directory.

### 2.2 The delivered body is a table of contents (critical)

`src/deliver.ts:108-115` builds a section map:

```
SECTIONS: §Review process §Apple's design principles
MORE: §Step 1: Establish context §Step 2: Load references — fetch via get_ref
```

and `src/deliver.ts:42` puts this in every body:

```
STYLE: no delve, tapestry, ... Full list: get_ref slop-patterns.
```

So the body says "fetch via get_ref" and the STYLE fence says
"get_ref slop-patterns", while `get_ref` cannot read anything. Three
independent breaks in the same contract:

- The path is broken (2.1).
- `slop-patterns` is not a per-skill file. It is `evals/slop-patterns.json` at
  the router root (`src/deliver.ts:22`). A per-skill fetcher can never resolve
  it. Confirmed: `skills/apple-design-skill/slop-patterns` does not exist.
- The body names **sections**, not files. The card stores section names and
  byte counts but no offsets (`src/types.ts:6-12`), and the names in the body
  carry `§` prefixes that are not in the source. `references/hig-lookup.md` is
  a real file, but nothing in the contract tells the agent that.

The section names do match the headings in `SKILL.md` (`## Review process`,
`## Apple's design principles`, `### 1) Offer + audience`), so a section-aware
fetcher is possible. It does not exist.

### 2.4 `ASK` on OpenCode delivers no body and no way forward (high)

```ts

  lines.push("Two skills fit and the router could not decide. Ask the user this question before acting:");
  lines.push(result.ask_question ?? "Which of these two do you want?");
```

The CLI's `formatResult` (`src/route.ts:158-172`) does include the body for
`ASK` and prints the council hint for `ABSTAIN`. The plugin drops both. So an
OpenCode agent that hits an `ASK` has a question, no skill, and no hint — and

### 2.5 The opencode instructions are silently discarded (high)

`~/.config/opencode/opencode.jsonc` contains:

```jsonc
"instructions": [
  "Skills are routed for you. A hook runs the pitmhskills router on the user's task before you see it, ...",
  "Session memory runs locally in claude-mem. Use the mem_search MCP tool, ..."
]
```

The opencode v2 config schema defines that key as:

```json
"instructions": {
  "type": "array",
  "items": { "type": "string" },
  "description": "Additional paths or URLs supplying ambient instructions"
}
```

Paths or URLs. The prose is treated as a path, does not resolve, and is
dropped — confirmed by its absence from the live system prompt, which contains
the project `AGENTS.md` and nothing else. The same applies to the claude-mem
instruction. The router's own `AGENTS.md:4` documents the council protocol,
but that file is only read by agents working **inside the router repository**;
an agent in another project never sees it.

**Fix:** put the text in a real file and reference it
(`"instructions": ["C:/Users/Mattchine/.config/opencode/instructions.md"]`),
and move the fallback instruction into the plugin's injection so it does not
depend on client config at all.

`src/gate.ts:12`:



Every other card is tier B (2,155) or tier A (20). The router can therefore

This is the direct answer to "it also failed to pick up some design skills".
Automatic routing can only ever land on the tier-B design cards, and those
are dominated by near-duplicates. The routing trace for one Apple HIG task
shows five of the top fifteen retrieval hits being HIG or mobile-design
variants of the same idea:

```
 2. apple-design-skill__apple-design      bm=28.9
 3. design__apple-hig-skills              bm=26.1
```

The collapse step keeps one winner per **cluster**, and clusters are

invoked deliberately. But it currently means the highest-craft design skills
are unreachable by routing, and the agent gets a tier-B substitute instead.
Either promote the ones that should route, or make the `ABSTAIN` result say
"a user-invoked-only skill matches this task" so the agent can ask for it by
name.

## 3. Skills and guides are not separated

The library mixes two different things under one card shape and one ranking:

| Kind | Example | What it is |
| --- | --- | --- |
| Procedure | `design-review__design-review` | numbered steps, a rubric, a report format |
| Reference | `accessibility-agents__kb-mobile-accessibility` | "Reference data, not a reviewer" |
| Theory | `laws-of-ux__laws-of-ux` | 30 laws with route selection and orchestration logic |

28 cards are `kb-` reference cards. `laws-of-ux__laws-of-ux` is a theory
engine, not a checklist, yet it competes in the same ranking and can win a
`PICK`, in which case the agent receives "Quick Reference / Orchestration
Logic / Route Selection" and no procedure for the task.

`src/types.ts` has `tier: "A" | "B" | "C"`, `domain`, `task_types`, and
`cluster_role`, but no field that says what the body *is*. Consequences:

- A theory card and a procedure card are ranked against each other with the
  same weights, and the theory card can win on vocabulary.
- A reference card wins and the agent has no procedure to follow, which reads
  as "the skill was bad" rather than "the wrong kind of thing was selected".
- There is no separate acquisition path. A guide is delivered as a skill body
  with the same fence and the same byte cap, so a 30-law theory is truncated
  the same way a procedure is.

### Proposed split

Add `kind: "procedure" | "reference" | "theory"` to the card schema, default
`procedure` for existing cards, and give the reference and theory classes
their own channel:

- **Separate ranking.** A `theory` card matches on topic, not on task shape.
  Give it a topic scorer over its headings and index terms, and keep it out of
  the procedure ranking entirely. A procedure is selected by "what should I
  do"; a theory is selected by "what do I need to know".
- **Separate acquisition.** A new MCP tool `consult(topic, question)` returns
  the relevant passages of a reference or theory card with citations, and is
  explicitly *not* a skill body. It has its own budget, because a theory answer
  is a lookup and a procedure is a commitment.
- **Separate outcome.** The router returns `PICK` (a procedure), `CONSULT` (a
  theory to consult alongside the procedure), or `PICK + CONSULT`. A design
  task that needs the laws of UX should get `design-review__design-review`
  **and** `laws-of-ux__laws-of-ux`, not one or the other.
- **Composition is bounded.** `config.json` already has
  `max_skills_per_task: 2`; extend it to "one procedure plus at most one
  guide", so the executor never carries two procedures and never carries a
  guide without a procedure.

The existing `pairs_with` field is the right shape for this: it already pairs
one extra core and is capped at one (`src/types.ts:107-110`). A guide is
exactly that, but sourced from a different pool.

## 4. The council

### Status: the plumbing is real, the product is not

The council is **not** part of the router. It is a side-channel generator: it
produces prompt strings for a caller to hand to subagents, collects verdicts,
and merges them. The router never spawns anything, never polls, and never
reads a council result back.

It is reachable. The MCP server exposes `council`, `note`, and `compose`
(`src/serve.ts:29-63`), and the CLI exposes the same three
(`src/cli.ts:106-108` → `src/cli-council.ts`). The full protocol runs:

```
$ bun src/cli.ts council "design a pricing page"
COUNCIL: cf7fcfe70e646ec8
CANDIDATES (4): mengto-skills__pricing-page score=99, design__copywriting-skill 59, ...
SPAWN PLAN (5 briefs, one subagent each): [critic] + 4 specialists

$ bun src/cli.ts note cf7f... mengto-skills__pricing-page keep "tier-A pricing builder, score 99"
$ bun src/cli.ts note cf7f... design__copywriting-skill drop "structure is out of scope"

$ bun src/cli.ts compose cf7f...
DECISION: mengto-skills__pricing-page confidence=99
MESSAGE: decided mengto-skills__pricing-page (2 survivors, 3 dropped)
DISSENT:
  dropped design__copywriting-skill: Pricing page structure is out of scope
  dropped awesome-copilot__gtm-technical-product-pricing: no verdict recorded
  dropped skills__monetizing-innovation: no verdict recorded
--- brief ---
<the full skill body>
```

| C-17 | Low | `src/council.ts:114-144` | A council opened with no candidates returns `ok` with an empty plan, writes an `open` row, and gives the agent no guidance and no fallback. |
| C-18 | Low | `src/council-store.ts:92-99` | Every prune statement is wrapped in a silent catch. |
| C-19 | Low | `src/council.ts:97-98` | `initCouncilSchema(db)` is called twice. |

### Nothing routes an agent into it

- The `ABSTAIN` branch of `route` returns a `council_hint`
  (`src/route.ts:91`) and the CLI prints it (`src/route.ts:169`). The OpenCode
  plugin drops the hint, and the `ASK` branch has no hint at all.
- The hint names `council(task)`, which is not a function any agent can call.
  The real entry points are the MCP tool `council` and
  `bun src/cli.ts council "<task>"`. The promise does not match the API.
- The protocol demands four specialists plus a critic, and a verdict per
  candidate. Nothing tells a model that it is allowed to do this, and the
  first thing an agent does with an `ASK` is ask the human.
- There is no fallback in any failure path. With no candidates, no notes, or
  all-drops, `compose` returns `skill_id: null` and an empty brief. The agent
  has spent five subagents and learned nothing, and still has to re-derive
  the answer.
- The council never writes back into routing. `src/route.ts` never reads
  `deliberations`, `composeCouncil` does not call `lockSkill`, and no
  `route_logs` row records the override. A later `route()` in the same session
  can pick a different skill and lock it, and the council's answer is silently
  ignored.

### What a council that actually gets used looks like

1. **Offer the council on `ASK`, not only on `ABSTAIN`.** When the margin is
   below the threshold and the top two are both procedures, the `ASK` result
   should carry `council_hint` too. The council's own threshold for spending
   a background round is exactly "two skills are within the margin".
2. **Use the router's near-tie set, not a half-floor pool.** The council
   should take the candidates the `route()` result already published, filtered
   by the same margin rule. That removes the nvidia noise at the source and
   makes the council's candidate set identical to the set the agent was shown.
3. **Make the hint executable.** It should carry the exact call, the reader
   cap, and the two follow-up calls.
4. **One tool, one lifecycle.** Replace the four-call protocol with a single
   `council` tool that owns the whole thing: it returns a decision, or a
   bounded `NO_CONSENSUS` with the deterministic `route()` answer attached as
   the fallback. Every exit path must return the deterministic answer.
5. **Bound the spend in the data.** Cap the readers at four total, cap the
   composed brief at the same 3,000 bytes the router delivers, sum
   `note.bytes` into a per-deliberation budget, and refuse to exceed it.
6. **Feed the result back.** `lockSkill` on the chosen id, a new
   `route_logs` outcome so the override is auditable, the skill's `verify[]`
   gates run at `phase_done`, and an eval-gated boost in the repo profile so
   the next similar task routes correctly without a council.
7. **Make the memory safe.** Server-generated ids only, validated against the
   table before any filesystem access, atomic note writes
   (write to `.tmp` then `renameSync`), `role` in the note key, membership
   checks on `skill_id`, survivors filtered by the current candidate list, and
   the `merge` rule either enforced or amended.
8. **Gate it.** Council cases in `tests/` and in `evals/`. The feature that
   can change which skill executes is currently outside the repo's own
   quality gate.

## 5. Why a skill can be missed: the index and scoring layer

Everything in section 2 is a delivery problem. This section is the routing
layer, and it contains the defect that explains most missed skills.

### 5.1 What is actually indexed

| Thing | Value |
| --- | --- |
| Raw `SKILL.md` files on disk | 2,331 |
| Reachable by the card builder's walk (depth ≤ 4, hidden dirs skipped) | 2,264 |
| Cards in `cards/` and rows in `pitmhskills.db` | 2,178 |
| Tier split | A = 20, B = 2,155, C = 3 |
| Top providers | `awesome-copilot` 447, `nvidia` 405, `mengto-skills` 176, `education` 165, `design` 157, `accessibility-agents` 108 |

**The skill body is never indexed.** Only the card's routing text is:
`purpose` + `use_when` + `keywords` + `domain` + `task_types`
(`src/index.ts:39-41`). A skill whose description is vague but whose body
says exactly when to use it is unroutable, because the only bridge is
`mineUseWhen`, which fires on three literal phrasings — "use when",
"triggers on", "should be used when" (`src/cardtext.ts:43`). **1,000 of
2,178 cards have a `use_when` of length 1**, meaning the description and
nothing else.

The embedding is not a model either. It is a signed-hash TF-IDF vector,
512 dimensions, pure JavaScript, stored as a JSON string in the `vecs` table
(`src/retrieve.ts:28-58`). Card vectors are stored **unweighted** while the
query vector is **IDF-weighted** (`src/retrieve.ts:133-142`).

### 5.2 The scoring formula, verbatim

`src/scoring.ts:136-166`:

```ts
const denom = s.denomKnown + s.unknownCount * maxIdf * weights.unknown;
const cover = denom > 0 ? Math.min(1, s.matchedMass / denom) : 0;
const bm = bmNorm(s.bm25, bm25Scale);
let score = 100 * (weights.bm25 * bm + weights.cover * cover + weights.vec * s.vec);
score *= Math.max(0.9, 1 - i * 0.02);                 // rank decay by list position
if (s.genericOnly) score *= GENERIC_FACTOR;            // 0.45
score += s.phraseBonus + s.predBonus + s.clause + s.primaryBonus
       - s.variantPenalty * weights.variant_unclaimed;
if (s.rareHit) score += weights.rare_match;            // +8
```

With `config.json`: `bm25` 0.35, `cover` 0.40, `vec` **0.05**. The score is
80 % lexical and 5 % vector.

### 5.3 The headline defect: common words are credited as identifiers

`scoring.ts:43` stems every query token. `scoring.ts:70` then calls
`lex.idf(w)` with that **already-stemmed** token. And `lexicon-stats.ts:51`:

```ts
idf(term: string): number {
  const d = df.get(stem(term)) ?? 0;      // ← stems a second time
  if (d === 0) return maxIdf;              // ← "unknown" means maximally specific
  return Math.log(1 + (n - d + 0.5) / (d + 0.5));
}
```

`stem()` is not idempotent, so the second stem misses the corpus and the
word is treated as **maximally specific**. Measured against the live
lexicon (`n = 2178`, `maxIdf = 8.380`):

| word | stem | second stem | df | idf **as used** | idf **if correct** |
| --- | --- | --- | --- | --- | --- |
| database | `databas` | `databa` | 19 | **8.380** | 4.716 |
| codebase | `codebas` | `codeba` | 42 | **8.380** | 3.937 |
| release | `releas` | `relea` | 23 | **8.380** | 4.530 |
| purpose | `purpos` | `purpo` | 21 | **8.380** | 4.619 |
| diagnose | `diagnos` | `diagno` | 36 | **8.380** | 4.089 |
| version | `vers` | `ver` | 37 | 7.281 | 4.062 |
| phase | `phas` | `pha` | 58 | 7.281 | 3.618 |
| **wizard** | `wizard` | `wizard` | **3** | **6.434** | 6.434 |

Read the last two rows together. **"database" (held by 19 cards) is worth
8.380. "wizard" (held by 3 cards) is worth 6.434.** The rarer word scores
lower. The design note at `src/weights.ts:29-34` states the intent exactly:
*"A word held by one or two cards out of 1456 is an identifier, not a topic:
'wizard' names exactly one skill."* The double stem inverts that for every
word whose stem changes.

The same double stem breaks the generic test at `lexicon-stats.ts:56`
(`isGeneric`), so a card matching only "database" is judged **specific** and
escapes the 0.45 generic penalty. And `rareHit` at `scoring.ts:73` uses the
single-stemmed `df.get(w)`, so the two checks disagree about the same word.

**Fix:** make `stem()` idempotent, or make `idf()` and `isGeneric()` accept
a pre-stemmed token, or key the df map on the same stem the query produces.
One line, and it changes the whole ranking.

### 5.4 Out-of-vocabulary words cost about 19 points each

`scoring.ts:144` charges unknown query words `maxIdf * weights.unknown`
(0.6) against the coverage denominator. Verified live on one card:

| Task | Score | cover |
| --- | --- | --- |
| `write a commit message for my staged changes` | 89 | 1.000 |
| the same, plus "in a polyglot monorepo" | 70 | 0.622 |
| the same, plus "in a zqxjkv polyglot monorepo" | 66 | 0.533 |

Three or four unknown words push an 89-point card below the floor of 45 and
the router abstains. This is the single easiest way to lose a good card, and
it explains the original complaint that the router abstains while the prompt
clearly contains enough keywords.

The FTS arm has the same problem in the other direction (`src/retrieve.ts:111-118`):
when a task has more than 12 tokens, the query keeps the **highest-idf**
terms, and `lex.idf` returns `maxIdf` for unknown terms. So an
out-of-vocabulary word **evicts** an in-vocabulary discriminating word from
the FTS query, where it matches nothing.

### 5.5 The cluster cap hides most of the library

`src/collapse.ts:166-168` keeps at most `max_per_cluster` (8) cards per
cluster. Live cluster sizes:

| cluster | cards | unreachable when the cluster fills |
| --- | --- | --- |
| `general` | 795 | 787 |
| `gpu-compute` | 430 | 422 |
| `workflow` | 298 | 290 |
| `frontend` | 292 | 284 |
| `frontend-design` | 88 | 80 |
| `cloudflare-edge` | 77 | 69 |
| `memory` | 72 | 64 |

The 2,159 template cards all land in one of these seven domains, and 795 of
them land in `general`. Verified live: the task *"how do I convert a pdf file
to markdown"* reported `capped = {"general": 13, "workflow": 1}` — 14 cards

### 5.6 Near-duplicate dedup makes whole families mutually exclusive

`src/collapse.ts:92-95` keys on provider plus the first ten words of the

```
deduped = ["web-animation__lottie-animation", "web-animation__gsap-web", "web-animation__micro-interaction"]
```

The 9 `web-animation__*` cards and the 18 `nvidia__doca-*` cards are
mutually exclusive: only one of each family can ever be a candidate. 31

`web-animation__micro-interaction` and left `web-animation__60fps-animation`
deduped instead.

### 5.7 A negative disambiguator clause can erase a card

`src/scoring.ts:106,121` subtracts `neg * CLAUSE_PENALTY` where the penalty
(34) is larger than the bonus (20). Verified live on
`anthropic__frontend-design`:

| Task | Score | clause |
| --- | --- | --- |
| "Build new distinctive UI from scratch for our landing page" | **75** (PICK) | +20.0 |
| "Polish and restyle this existing UI, an audit of the current interface" | **−6** (dropped) | −29.0 |

One negative clause knocked the card out of contention entirely. 41 cards
carry a negative clause; the other 1,989 have no clause signal at all, so the
whole clause mechanism is available to a small curated minority.

### 5.8 The generic penalty is nearly dead code

`GENERIC_FRACTION = 0.18` gives a threshold of 392 for this corpus, and only
**12 terms** exceed it: `implement` 1802, `or` 926, `general` 850, `design`
788, `to` 703, `debug` 691, `review` 681, `skill` 631, `workflow` 548,
`comput` 439, `gpu` 436, `user` 394. A card matching only "design" is
penalised 0.45×. A card matching only "database" is not — because the double
stem hides it from `isGeneric`.

### 5.9 The rare-word bonus rewards junk

`scoring.ts:73` grants +8 when a matched term has `df ≤ 2`. **4,343 terms
qualify**, including `msaa`, `sizer`, `narrator`, `cla`, `549`, `sarif`,
`treemap`, `donut`. A card holding one of those gets +8, enough to flip a
close ranking.

### 5.10 The synonym table misses stemmed tokens

`src/lexicon.ts:158` looks the token up in `SYNONYMS` by its **raw** group
key, but `scoring.ts:43` passes a stemmed token. `stem("routing")` is
`"rout"`, which is not a key in the group `["route","router","routing","routed"]`,
so the route/router synonym never fires for "routing". The same class of
failure applies to any group member whose stem leaves the group.

### 5.11 The card cache is keyed on the row count only

```ts
function dbKey(db: Database): string {
  const row = db.query<{ n: number }, []>(`SELECT count(*) n FROM cards`).get();
  return String(row?.n ?? 0);            // src/retrieve.ts:175-182
}
```

A re-index that keeps the same card count leaves a long-lived process — the
MCP server — serving the **old** card text and the **old** vectors.
`invalidateLexicon()` exists at `src/lexicon-stats.ts:90-92` and is called
from nowhere.

### 5.12 Absolute `skill_path` and a filtered card set

`src/card.ts:192` writes an **absolute Windows path** into the card, so on
another machine `loadBody` cannot read the file and falls back to a
synthetic stub (`src/deliver.ts:72`): the skill still routes, and the agent
receives a title and a purpose instead of the skill. The curated cards in
this repo use relative paths and are fine.

Separately, `.gitignore:10-21` excludes whole card families whose licences
are not recorded, and 760 cards in the live database still say
`license: "UNKNOWN"`. **A fresh clone has fewer cards than this machine.**
`license_allow` in `sources.yaml` is declared but never enforced in code
(`src/ingest.ts:26,33`).

## 7. Method and limitations

- All routing results were produced with `bun src/cli.ts route "<task>"`
  from the router root with `--cwd C:\Users\Mattchine\portfolio`, and through
  the MCP `route` tool.
- `get_ref` was called through the MCP tool exactly as an agent would.

  `~/.codex/hooks.json`, `~/.claude/settings.json`, `~/.claude.json`,

  The margin distribution, not the PICK rate, is the meaningful signal, and
  that comes from the decision rule rather than the sample.
- `claude-mem` was not running during this session, so nothing was written to
  the memory index.
